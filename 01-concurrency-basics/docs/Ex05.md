# ForkJoinPool 사용보다 Executor를 지정하는게 좋다.

`Ex05` 출력에서 이 줄을 보셨을 겁니다.

```
[  203 ms] [main] (3) commonPool parallelism = 21
```

이 숫자가 핵심입니다. 지금 개발 머신은 코어가 많아 21이지만, **운영 서버 컨테이너가 2코어면 이 값이 1**이 됩니다. `commonPool`은 `CPU 코어 수 - 1` 로 고정되기 때문입니다.

## 1. commonPool은 "내 Pool"이 아니다

이름 그대로 JVM 전체가 **공유**합니다. 나도 모르게 같이 쓰는 것들이 있습니다.

- `list.parallelStream()` — 전부 commonPool에서 돕니다
- `Arrays.parallelSort()`
- Executor를 지정하지 않은 **모든** `supplyAsync` / `thenApplyAsync`
- 내가 쓰는 라이브러리 내부 코드

즉 내 비동기 작업이 남의 `parallelStream`을 막고, 반대도 성립합니다. 서로의 존재를 모르는 코드끼리 같은 Thread 몇 개를 두고 경쟁합니다.

## 2. 크기가 CPU 기준이라 Blocking I/O에 안 맞다

`ForkJoinPool`은 원래 **CPU를 태우는 계산 작업**을 잘게 쪼개 돌리려고 만든 물건입니다. "코어 수만큼만 있으면 충분하다"가 전제입니다. 그런데 외부 API 호출은 CPU를 안 쓰고 그냥 **기다리기만** 합니다.

4코어 서버(parallelism = 3)에서 1초짜리 외부 API를 100번 호출한다면:

| | Thread 수 | 소요 시간 |
| --- | --- | --- |
| commonPool | 3 | 약 34초 |
| 전용 Pool(50) | 50 | 약 2초 |

Ex09에서 실측했던 것과 같은 이야기입니다. Pool 2개에 400ms 작업 4개를 넣으니 813ms가 걸렸죠. Thread 수가 그대로 처리량 상한이 됩니다.

그리고 그 34초 동안 **commonPool을 쓰는 다른 모든 코드가 같이 멈춥니다.**

## 3. 장애가 격리되지 않는다

Pool을 용도별로 나누는 걸 bulkhead(격벽) 패턴이라고 합니다. 배가 침수돼도 한 구역만 잠기게 하는 것과 같습니다.

```kotlin
val paymentExecutor = namedFixedPool("payment", 20)
val notificationExecutor = namedFixedPool("notification", 10)
```

결제 API가 죽어서 타임아웃 30초씩 걸려도 `payment` Pool만 포화되고, 알림은 정상 동작합니다. commonPool 하나에 다 올렸다면 결제 장애가 서비스 전체 장애가 됩니다.

## 4. 그 밖에

- **모니터링** — Thread 이름이 전부 `ForkJoinPool.commonPool-worker-N`이라 스레드 덤프를 떠도 누가 뭘 하다 막혔는지 알 수 없습니다. 예제에서 Pool 이름을 `io-1`, `cpu-1`로 붙인 이유입니다.
- **종료 제어** — commonPool 스레드는 daemon이라 JVM 종료 시 작업을 기다려 주지 않습니다. 진행 중이던 작업이 그냥 사라집니다. `shutdown()`을 호출해도 무시됩니다.

## 정리

> commonPool은 **CPU 계산 작업 전용**입니다. Blocking I/O를 올리는 순간 전제가 깨집니다.

로컬에선 코어가 21개라 티가 안 나고, 코어 적은 운영 컨테이너에서 터집니다. 그래서 Ex05에서 용도별로 나눈 겁니다.

```kotlin
val ioExecutor = namedFixedPool("io", 10)   // Blocking I/O: 코어 수보다 크게
val cpuExecutor = namedFixedPool("cpu", 4)  // 계산: 코어 수 정도
```

Ex06 (2)번에서 `supplyAsync`는 `ioExecutor`로, 뒤이은 변환은 `thenApplyAsync(..., cpuExecutor)`로 넘긴 것이 이 원칙을 적용한 예입니다.

> 참고로 Java 21+ 가상 스레드(`Executors.newVirtualThreadPerTaskExecutor()`)를 쓰면 Blocking I/O의 Thread 수 제약 자체가 없어집니다. 다만 그건 "Pool을 안 나눠도 된다"가 아니라 "I/O용 Pool 크기 고민이 사라진다"에 가깝습니다.
